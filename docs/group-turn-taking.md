# 群聊发言权设计：意图 + 仲裁

> 状态：设计稿，待实施。
> 目标：把「谁该发言」从写死的字符串规则，换成「模型给语义判断 + 代码做仲裁」的机制。

---

## 1. 问题的证据

2026-08-28，群「暴富」（5 成员）中的一条真实用户消息：

```
大家有什么需要都说一下，需要支持直接找 @幕僚长 ，他有我所有权限，
如果大家都收到了就回复一下，欢迎一下我们的新伙伴
```

背景：**幕僚长是当天 18:46 刚加入的新成员**（次新成员早了一整天），也就是这句话里要欢迎的「新伙伴」。

作者意图无歧义：**用户在向全员介绍新人并要求全员回应**（「大家…都回复一下」「欢迎一下我们的新伙伴」）。`@幕僚长` 是被介绍的对象，不是被寻址的对象。

实际路由结果（已复现，见 §6 回放用例）：

```
parseGroupMentions -> { isEveryone: false, memberIds: ["幕僚长"] }
resolveResponders  -> 幕僚长            ← 只有他一个
```

实际发生的事（转录 #74–#79 + `[group-chat]` 审计日志）：

| # | 发言者 | 内容 | 是否响应了用户的请求 |
|---|---|---|---|
| 75 | 幕僚长 | BTC 微观盘口 | 否 |
| 76 | 幕僚长 | `@全员` 分派任务 | 否 |
| 77 | 系统分析师 | $78k 共振补充 | 否 |
| 78 | 宏观分析师 | 宏观决策树 | 否 |
| 79 | 幕僚长 | 收尾定调 | 否 |

**速报员、股票技术分析全程没发言。没有任何人欢迎新伙伴，没有任何人回复「收到」。**

### 1.1 两个独立的失败

**失败 A —— S2 被误判成 I1。**
`@幕僚长` 在这句话里是**第三人称指称**（「需要支持直接找 @幕僚长，**他**有我所有权限」），是在跟大家介绍他，不是在对他说话。研究文献里这叫 S2（Referenced but Not Addressed），正确处理是**不因此获得发言权**。原话：*being talked about is not the same as being talked to*。

当前代码把任何 `@` 一律当成排他性寻址，于是 S2 直接把响应集合坍缩成了一个人。

这里的反讽值得记下来：**唯一不该独自应答的人（刚进群、正被介绍的新人），成了唯一被授予发言权的人。** 用户是在向全员谈论他，系统把这理解成了在对他说话。

**失败 B —— 自然语言寻址完全不可见。**
`GROUP_EVERYONE_HANDLES = ["everyone", "all", "所有人", "全员", "大家"]` —— **「大家」本来就在列表里**，但 `parseGroupMentions` 只扫描 `@` 前缀的 token：

```
"大家都回复一下"      isEveryone = false     ← 用户的实际写法
"@大家 都回复一下"    isEveryone = true
"所有人都说说"        isEveryone = false
"@所有人 都说说"      isEveryone = true
```

用户用中文明确说了「大家都…」，系统只认 `@大家`。

**失败 C（次生）—— 机器人扩散房间。**
`resolveResponders` 扫描 last-user 之后的**所有**消息，包括 bot 自己的。幕僚长在 #76 说了 `@全员`，于是第二轮响应集合被一个机器人单方面扩散成全员：

```
round0 responders -> 幕僚长
round1 responders -> 幕僚长, 速报员, 系统分析师, 股票技术分析, 宏观分析师
```

后面几个人是被**机器人的协调消息**选举进来的，不是被用户的请求选举进来的——这解释了为什么他们答的全是上一个话题，没人回应用户。

### 1.2 结论

这三个失败有同一个根因：**寻址判断是用字符串匹配做的。**

修法**不是**往 `GROUP_EVERYONE_HANDLES` 里加 token、也不是给 `@` 加个「是否第三人称」的正则。那只是把失败点往后挪一格。「大家」这个词已经在列表里了，它依然失败了——这本身就是「写死规则」这条路走不通的证明。

## 1.3 判据实验：是模型能力问题还是代码逻辑问题？

2026-08-31，用本机 freeroute（`auto`）在 27 条标注语料上实测。语料取自真实转录 +
文献分类的合成边界用例；标注为「作者真实意图」。复跑：`npm run bench:routing`，
原始输出见 [`routing-benchmark-2026-08-31.txt`](./routing-benchmark-2026-08-31.txt)。

| 方案 | 总体 | 困难用例（4） | 简单用例（23，回归保护） |
|---|---|---|---|
| 现状正则 | 81.5% | **0%** | 95.7% |
| 模型 · 朴素提问（v1） | 43.2% | — | 明显退步 |
| **模型 · 语义区分提问（v2）** | **97.5%** | **83.3%** | **100%** |

### 结论：是代码逻辑问题。

三条独立证据：

1. **路由链路上零模型调用。** `resolveResponders` 是纯同步字符串函数，寻址判断
   100% 由正则做出，模型从未被问过。所以「模型能力不足」在当前架构里根本无从谈起。
2. **模型被正确提问时能做对。** v2 在困难用例上 83.3%，而且**在简单用例上 100%，
   不退步**。它甚至能正确返回空集（`s02` 纯致谢 → 无人发言）—— 这是现状架构
   结构性做不到的事（`resolveResponders` 返回值恒非空）。
3. **正则的错误没有方向。** 多说 3 例、少说 2 例。它不是「太爱说」或「太沉默」
   这种可调偏置，而是没有语义信号。阈值调不出来，因为信息不在里面。

### 但有一个必须记住的陷阱：**朴素地接模型比不接更糟。**

v1（只问「谁该回应？」）总体 43.2%，**低于正则的 81.5%**。它在
`"为啥超时了？ @系统分析师"` 这种最简单的直接寻址上都会 0/3 —— 拉进多余的人。
这正是文献说的 speak bias：模型倾向于让更多人参与。

v2 与 v1 的唯一差别是提示词里那几句语义约束：

> - 「被谈论」不等于「被对话」。有人被 @ 或被提到名字，可能只是被介绍、被表扬、
>   被转述——这种情况他**不因此获得发言权**，真正被问的是别人。
> - 寻址可以完全不带 @。「大家」「你们」「都说说」「各位」同样是在对全体说话。
> - 承接上文的追问（没有主语）通常是在问上一个发言的人。
> - 纯粹的告知、致谢、确认，可能不需要任何人回应。

**所以平衡点不在「用不用模型」，而在「怎么问」。** 这几句约束是本设计里最关键的
资产，改动它们必须重跑基准。

### 一处标注存疑（诚实记录）

`r74` v2 只有 1/3，但它三次里两次答的是「除幕僚长外的全部四人」。考虑到幕僚长
正是那句话里要被欢迎的新人——**不该让一个人欢迎他自己**——模型的答案可能比我的
标注（全员）更合理。若采纳模型读法，v2 困难用例为 100%。

这也印证了文献的观察：这类判断本身存在真实歧义（人类标注者间 κ = 0.492，
人类平衡准确率仅 60–66%）。不要把目标定成 100%。

## 2. 设计原则

**语义判断交给模型，仲裁交给代码，上限只做断路器。**

| 层 | 谁负责 | 内容 |
|---|---|---|
| 语义 | 模型 | 我被叫到了吗？这轮我有必要说吗？为什么？多紧迫？ |
| 仲裁 | 代码（确定性，零 LLM 调用） | 谁先说？还有人要说吗？本轮结束了吗？ |
| 断路 | 代码 | 防跑飞的硬上限，**正常情况下永不触发** |

关键的线在于：**代码只对模型给出的语义判断做排序，它自己不做语义判断。** `@` 不再是门禁，它降级成喂给模型的一个特征。

三条必须守住的约束：

1. **不写死策略。** 不出现「含 X 词则全员」这类规则。
2. **保留自主性。** 每个成员自己决定要不要举手，系统不替它决定。
3. **终止来自机制。** 「没人举手 → 本轮结束」是自然结果，不是靠数轮数。

## 3. 架构

### 3.1 意图（模型产出）

每个候选成员产出一个结构化意图。这是一次**廉价调用**：不给工具、不要长文本、只要结构化输出，几十个 token。

```ts
interface SpeakIntent {
  /** 我这轮想发言吗 */
  wantsToSpeak: boolean;
  /** 紧迫度 1-5：1=可有可无，5=直接点名我了/我有关键信息 */
  urgency: 1 | 2 | 3 | 4 | 5;
  /** 一句话理由，进日志，不进房间 */
  reason: string;
  /** 我如何理解自己被寻址的方式（对应文献 I1/I2/S1/S2） */
  addressing: "addressed" | "participant" | "bystander" | "mentioned-only";
}
```

`addressing` 这一项由**模型判断**，不由正则判断。上面那条真实消息，正确的输出应该是：

- 幕僚长：`mentioned-only`（被介绍，不是被问）→ 但「大家」包含他 → `participant`
- 其余四人：`participant`（「大家…都回复一下」直接寻址到他们）

### 3.2 仲裁（代码，确定性）

```
输入：全体成员的 SpeakIntent + 房间状态
输出：本轮发言人（或 null = 本轮结束）

1. 过滤 wantsToSpeak = false
2. effectiveUrgency = urgency + silenceBonus(member)
     silenceBonus 随该成员连续未发言轮数递增（上限 +2）
     —— Inner Thoughts 的 silence decay，防止某成员被系统性埋没
3. 过滤 effectiveUrgency < THRESHOLD
4. 按 effectiveUrgency 降序；平局时静默更久者优先
5. 取 top 1 授予发言权；空集 -> 本轮结束
```

注意仲裁里**没有任何关于 `@`、关于中文词、关于角色的硬编码**。它只对模型给的数字排序。

### 3.3 循环

```
while (未达断路上限):
    收集全体意图                 ← N 次廉价调用（可批量成 1 次）
    winner = 仲裁(意图集合)
    if winner == null: break     ← 机制性终止
    winner 完整生成（带工具）      ← 1 次完整调用
    发布到房间
```

对比现状：现在是 **N 次完整生成**（每人一次带工具的完整轮次）。新方案是 **N 次廉价举手 + 1 次完整生成**。成员越多，省得越多。

### 3.4 `@` 的新位置

`@` 不再是门禁，而是喂给意图步骤的一个**信号**：

- 用户的 `@X` → 在给 X 的意图提示里注明「用户直接点了你」，X 大概率自评 `addressed` / urgency 5
- 用户的 `@X` → **不再排除其他人**，其他人照常举手，靠仲裁排序自然落后
- bot 的 `@Y` → 作为一条弱信号给 Y，**不授予任何发言权**，也不扩散房间

这样第 1 节的三个失败同时消失，而且都不是靠新增规则消失的。

### 3.5 显式交接

Grok Bots 的 "pass ownership" 原语保留为一个**工具**，不是 `@` 解析：

```
Handoff(to: memberId, task: string)
```

被交接者在下一次仲裁里获得 urgency 加成。这条路径是显式的、可审计的、不可级联（一次交接不能再触发下一次自动交接，防链式放大）。

### 3.6 沉默也变成结构信号

`(pass)` 字符串退役为兜底。首选路径是 `wantsToSpeak: false` —— 结构化字段，不存在 `(pass)+commentary` 这类带内哨兵的解析问题（AutoGen 的 `"TERMINATE"` 有完全相同的已知缺陷）。

## 4. 硬上限的正确用法

`GROUP_MAX_ROUNDS` / `GROUP_MAX_MEMBER_TURNS` **保留**，但语义改变：

- 现在：主要的收敛力量
- 之后：断路器，正常永不触发

必须配套：**触发上限时打一条 warn 级日志**，并计入指标。

- 上限从不触发 → 机制有效
- 上限经常触发 → 机制失效，去修机制，不要调大上限

这是把「效果还不错」从肉眼判断变成客观度量的关键。

## 5. 分阶段实施

每一阶段独立可用、独立可回滚。

| 阶段 | 内容 | 新增推理调用 | 风险 |
|---|---|---|---|
| **0** | 影子模式：新仲裁与旧路由并行计算，**只记日志不改行为** | 0（先用启发式意图） | 无 |
| **1** | 断路上限告警 + 指标 | 0 | 无 |
| **2** | bot 的 `@` 不再授予发言权 / 不再扩散房间 | 0 | 低 |
| **3** | 接入真实意图调用，仲裁开始生效 | N 次廉价 | 中 |
| **4** | `Handoff` 工具 + `wantsToSpeak` 取代 `(pass)` | 0 | 中 |

阶段 0 是关键：**先在真实流量上观察新机制「本来会怎么判」，再让它真的生效。**

## 6. 验证方案（必须可恢复）

### 6.1 绝不碰生产数据

- 所有自动化测试使用**隔离 dataDir**（`test/integration/helpers.mjs` 的既有做法）
- **绝不**对 `~/.sdk-bots` 跑测试
- 手工联调前先备份：`cp -a ~/.sdk-bots ~/.sdk-bots.bak.$(date +%s)`

### 6.2 回放语料（golden tests）

把真实转录里的失败案例固化成单测 fixture，**不依赖网络、不依赖模型**：

```
test/unit/fixtures/group-routing/
  msg74-welcome-newcomer.json     ← §1 那条，期望：全员，不是只有幕僚长
  bot-at-everyone-escalation.json ← bot 说 @全员 不得扩散房间
  third-person-mention.json       ← S2 不得授予发言权
  direct-address.json             ← I1 必须授予（回归保护）
```

每个 fixture 存：房间成员、消息序列、**期望的仲裁结果**。这些用例在改动前先跑一遍确认「现在是红的」，改完确认变绿。

### 6.3 影子模式的观测

阶段 0 上线后，日志里同时记录两条：

```
[group-route] legacy=[幕僚长] shadow=[幕僚长,速报员,系统分析师,股票技术分析,宏观分析师] msg="大家有什么需要…"
```

跑一段真实使用后统计两者分歧率和分歧方向，再决定阶段 3 是否放行。

### 6.4 回滚

- 单一环境变量开关：`SAND_GROUP_ARBITRATION=off|shadow|on`，默认 `shadow`
- 每个阶段一个独立 commit，可单独 revert
- 在**独立分支**上做，不直接推 `main`
- 旧的 `resolveResponders` 保留原样，不删除，直到阶段 3 稳定运行一段时间

### 6.5 每阶段的验收门槛

```
npm run typecheck
npm run test:unit          # 含新增 golden tests
npm run test:integration   # 8 个隔离用例
npm run test:e2e           # mock 群聊回环
```

全绿才进下一阶段。

## 7. 已知的开放问题

1. **意图调用的成本**：N 次廉价调用能否批量成 1 次？批量会让判断重新中心化（回到选举器），失去自主性。需要实测取舍。
2. **意图步骤的发言偏置**：模型自评「我要不要说」同样有 speak bias（文献证实零样本模型有强发言偏好，且这是能力缺失而非指令不遵）。`THRESHOLD` 的初值需要靠影子模式的真实数据标定，不能拍脑袋。
3. **用户信号的利用**：用户追问 / 用户说「别废话」/ 用户重新提同一问题 —— 这些是天然的偏好标注，是本系统相对论文的独有优势。如何采集和利用，另行设计。
4. **进度提示占用发言额度**：`GROUP_MAX_MESSAGES_PER_TURN = 2` 现在允许「进度提示 + 答案」。严格的一轮一发言下，进度提示应彻底不进房间消息流（console 已渲染为可折叠状态注记）。
